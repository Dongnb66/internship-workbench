# FAQ

## 产品定位

**这个工具到底解决什么问题？**
求职信息散在 BOSS、实习僧、邮箱、备忘录、Excel 里，导致三件事做不好：该投的没投、投了的没跟进、聊过的忘了聊到哪。本工具把「岗位池 → 投递 → 沟通 → 面试 → Offer」收在一条线上，用一张投递看板回答「我现在卡在哪一步」。

**它和招聘 App 的关系？**
不替代、不对接。工作台**不登录**任何招聘平台、**不自动**投递、**不自动**发消息、**不抓取**你的平台会话。所有数据由你手工录入或粘贴，它只做管理。

**为什么不做自动投递？**
两个原因。一是平台风控——脚本化批量投递几乎必然触发账号限制，收益远小于风险；二是这类动作的收尾责任在你身上，出问题时解释不清。所以本项目的自动化只停在「帮你把话术写好、把表填好、把该跟进的挑出来」，**发送键始终由你按**。

## 使用

**第一次用要先注册吗？**
不用。登录页默认就是「验证码登录 / 注册」——填邮箱、收验证码、提交，**首次使用会同时完成注册并登录**。如果希望以后能用密码直接登录，在验证码那一栏里顺手设一个至少 6 位的密码即可（已有密码的账号留空就行）。所以不存在「先注册再登录」这一步。

**为什么网页端不能手机号 / 短信登录？**
不是没做，是**这个平台的网页端不提供**。认证服务的支持边界是明确的：邮箱验证码、邮箱密码在网页端和小程序端都可用；**手机号短信验证码和微信登录只在小程序端可用**。在网页端加这个入口，代码能编译通过，但运行时一定失败——因为上游没有给网页端开放短信通道。

**那手机号 / 微信登录怎么办？**
已经做了：`miniprogram/` 是同一套云后端上的微信小程序端，直接提供**手机号短信验证码登录 / 注册**与**微信一键登录**。数据模型没改，两端共用同一个账号和同一批表——手机上记一条跟进，电脑上刷新就能看到。本地打分、投递节奏守则、打招呼自检清单与网页端是同一份口径（`utils/` 下的纯逻辑移植），不是两套规则。桌面独有的模块（面试日程、Offer 对比、简历库、知识库）仍留在网页端。

**为什么本地 `localhost:5173` 登录不了？**
邮箱验证码登录 / 注册在服务端做了 Origin 校验，只在应用的正式发布域上可用。这是安全设计，不是 bug。本地开发时如果想完整调试登录流程，需要把 `src/cloud.ts` 的 `endpoint` 指向你自己部署的实例并放行本地 Origin。

**第一次打开，岗位池为什么是空的？**
因为它不会自己长出数据 —— 这不是 bug，是有意的。岗位池的价值在「你放进去之后」才显现（匹配度、投递节奏、超期提醒都建立在它之上），所以空态给的是入库通道：

1. **岗位广场**（最省事）：左边栏「岗位广场」是所有人共享的公共岗位库，点「加入岗位池」就把岗位复制进你自己的池子，不用自己抓。它和你的岗位池是两回事：广场只读、人人可见，点加入后那份副本才归你，匹配度与备注都只属于你。
2. **浏览器助手采集**：在招聘结果页点「采集本页岗位」，读当前已渲染的 DOM，一键复制 → 工作台「批量导入」→ 粘贴 → 读取。
3. **本地抓取器**（批量）：`cd crawler && npm run crawl -- --site tencent`，它自己翻页、逐个补 JD，产出 `crawler/output/*.json` 后在「批量导入 → 选择抓取结果文件」里选它。
4. **整段粘贴**：把招聘页 / 邮件 / 群里的岗位信息整段复制，粘进「批量导入」，会自动拆成公司 / 岗位 / 城市 / 薪资 / 截止 / JD 正文。连扩展都不用装。
5. **示例数据**：点「导入 5 条示例岗位看看」，立刻体验匹配度、批量评分、转投递的完整链路，看完一键清空。

**岗位广场和岗位池有什么区别？为什么是两个东西？**
因为「公共的岗位数据」和「我对某个岗位的私人进展」本质是两类数据：

| | 岗位广场 | 岗位池 |
| --- | --- | --- |
| 谁能读 | 所有人 | 只有你 |
| 谁能写 | 没有人（只由工作台侧灌入） | 只有你 |
| 有匹配度 / 备注 / 投递状态吗 | 没有 | 有 |

这个拆分解决的是一个真实问题：工作台按账号隔离数据，如果只有「私有岗位池」，每个新用户打开都是空的（连你自己换个账号登录也一样），看不出这个工具的价值。所以广场负责「数据从哪来」，岗位池负责「我怎么跟踪它」。你在广场点「加入岗位池」时，它是**复制**一份快照给你的 —— 之后广场就算更新了那条岗位，也不会动你已经在跟进的记录。

**岗位广场的岗位会每天自动更新吗？**
不会。它不会自己刷新，内容是工作台侧灌入的（真人跑一次抓取 → 清洗 → 入库），新鲜度取决于最后一次灌入时间。页面上每条岗位都标了采集时间，请以那个时间为准。想要更新的数据，用本地抓取器在你自己机器上跑一次，导入到自己的岗位池。

**为什么不直接爬 BOSS / 官网，做成每天更新的岗位库？**
服务端那半边**不做**，本地那半边**已经做了**（`crawler/`）。三点原因决定了这个分界：

- **服务端没有落点。** 这个项目是云上的静态站点 + 云数据库，没有常驻后端进程，也没有浏览器内核。真实抓取需要 Chromium 一直跑着 —— 那只有桌面软件或本地脚本才有的形态。
- **风控后果落在你的账号上，而且这一条没有消失。** 招聘平台的搜索结果接口有加密参数、频控和滑块，绕过它们意味着用**你自己的登录态**去工厂化抓取。轻则限流、验证码升级，重则封号 —— 而封的是你要用来投简历的那个号。所以本地抓取器在这方面是**刻意保守**的：严格串行、每次请求之间强制等待且带随机抖动、单站点页数有上限、不调平台接口、不解密参数、不绕登录与验证码，只读浏览器**已经渲染出来**的 DOM。风险不是被消除，而是从「你完全不知情」变成「你看得见、随时能停」。
- **第三方平台的公开岗位数据是有条件的。** 各家都禁止未授权的大规模抓取，这不是可以「技术上做到所以做」的事。

所以本项目把自动化**停在「你自己看得见的那一屏」**，四条通道的区别只是「谁来点」：岗位广场（点一下加入）→ 整段粘贴（全手动）→ 浏览器助手（手动点一次）→ 本地抓取器（自己翻页）。读的都是渲染后的 DOM，采集结果里不会出现你没看到的内容。代价是效率仍然受你机器和账号的限制，收益是账号安全、来源可溯。

**本地抓取器要装什么？会动我的浏览器吗？**
`cd crawler && npm install` 装一个 `playwright-core` 就够了 —— **不会下载几百 MB 的浏览器内核**，它直接驱动你系统里已有的 Edge 或 Chrome（找不到才提示你装）。它用一个独立档案目录（`crawler/.profile`），不碰你日常浏览器的书签、密码和登录状态；需要登录的站点由你自己跑 `node login.mjs` 在那个独立窗口里登一次，脚本全程不读取、不打印、不上传任何 cookie 内容。抓不到东西时先加 `--dump` 把渲染后的 HTML 存下来，看页面到底长什么样。

**「匹配度」是怎么算的？**
两层。第一层是本地规则打分（`src/lib/score.ts` 的 `localScore`）：按画像里的技能关键词、目标城市、目标岗位类型、期望薪资与 JD 做加权匹配，秒出结果、零成本。第二层是 AI 七维深评（`evaluateJD`），更准但慢且耗 token。所以批量评分用的是两段式流水线：**先用本地分预筛（阈值 45），通过的才送 AI**，避免为明显不匹配的岗位白烧额度。

**为什么批量评分是串行的、还这么慢？**
故意串行。并发请求容易触发限流，且失败后难以定位是哪一条。串行 + 实时进度 + 可中断 + 失败可单独重试，比「快但一整批失败了不知道哪条挂了」更实用。

**「匹配度」低于多少不该投？**
没有绝对阈值，建议 < 55 的先放一放——不是你不能投，而是同样的时间投匹配度高的岗位回报更高。JD 里有一半以上你完全没接触过的技术时，简历大概率过不了初筛，投了也是消耗心态。

**打招呼话术能直接用吗？**
**不能。** 生成结果里有几处刻意的约束（不出现校名、不提没做过的技术、数字口径与简历一致、长度匹配对方问题强度），但语气仍然是模型写的。正确用法：读一遍，改成你平时说话的样子，留一处不完美。模板腔的话术 HR 一天看几十条，一眼就能认出来。

**为什么登记「已发打招呼」前必须勾 6 条清单？**
那是投递纪律的可执行版本。清单里的每一条都对应一个真实踩过的坑——写校名被筛、提了没做过的技术被追问、数字和简历对不上被 clone 打脸。勾选不是仪式，是让你在按发送键之前停三秒。

**「今日投递节奏」是限制我吗？**
不是。它防的是两件更伤的事：一天群发几十条被平台判定骚扰导致账号受限；以及投太散导致后续跟进不过来，等于白投。默认值（8 条 / 09:00–21:00 / 间隔 30 分钟）可以按自己情况改。

**「超期未回复」多少天算超期？**
默认 7 天（`staleApplications(apps, msgs, 7)` 的第三个参数可调）。判断依据是「该投递最近一次沟通时间」与「投递时间」里的较晚者。到 14 天以上标红——这个阶段继续等回复的期望收益很低，应该换渠道或者把精力转到别的岗位。

## 技术

**为什么不用 UI 组件库 / 图表库 / 状态管理库？**
因为项目的复杂度撑不起这些依赖的成本。11 个页面、纯表单和表格，手写 CSS + 原生 SVG 完全够，还换来零版本冲突、零样式覆盖战争、构建产物小。这是权衡后的选择，不是「为了显得硬核」。

**前端把 key 写进源码，安全吗？**
`publishableKey` 是发布级公开 key，写进前端是设计如此。数据隔离靠数据库 RLS（每张表 `owner_id = auth.uid()`），不靠隐藏 key。详见 [`CONFIGURATION.md`](CONFIGURATION.md) 第 3 节。

**写操作返回空数组是什么意思？**
被 RLS 拒绝了。PostgREST 语义下策略拒绝不抛错，返回空数组。所以 `src/lib/api.ts` 的 `insertRow` / `updateRow` 都有显式判空并抛错——这是数据隔离的第一道可见防线，不要删。

**AI 是怎么参与开发这个项目的？**
功能优先级、数据模型、RLS 策略、是否发布由人决定；组件代码与文案初稿由 AI 起草，最终措辞由人改成自己的语气。仓库根目录的 [`AGENTS.md`](../AGENTS.md) 把这条界线写成了可执行的规范，任何 AI 工具进仓库前先读它。

**为什么不提交导出的 JSON 备份？**
备份里含手机号、邮箱等个人信息，且体积不小。已在 `.gitignore` 中排除。

## 边界与免责

**AI 给的评估准吗？**
它是基于你录入的 JD 文本和画像做的文本匹配与推理，**不是**对岗位或公司的真实判断。JD 写得含糊、或公司故意放大要求时，结论会偏。把它当参考，不要当结论。

**能保证拿到 Offer 吗？**
不能，也不该指望工具保证。它解决的是「流程混乱」这一层问题；能不能过，取决于你的项目、基础和表达。工具能做的只是让你别因为忘记跟进、投错方向、话术踩雷而白白丢掉机会。

**数据存在哪？**
存在你登录的云服务实例里，按账号隔离，只有你自己能看到。可在「配置 → 数据」导出完整 JSON 备份。
